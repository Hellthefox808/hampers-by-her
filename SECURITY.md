## 1. Security Principles & Defense-in-Depth

The Hampers by Her security architecture implements five non-negotiable principles:
1. **Zero Implicit Trust**: Every API endpoint, WebSocket frame, and database transaction must establish and verify identity and tenant boundary.
2. **Deterministic Security Controls**: Security boundaries and authorization rules are enforced in deterministic compiled code and database engines, never delegated to non-deterministic LLM evaluation.
3. **Hardware Tenant Isolation**: Row-Level Security (RLS) is enforced at the database kernel level; application logic errors cannot cause cross-tenant data bleed.
4. **Human-in-the-Loop Confirmation Gates**: No autonomous agent or voice command can execute a state-modifying or external egress action without explicit cryptographic user confirmation.
5. **Untrusted Evidence Isolation**: All retrieved documents, webhooks, and third-party inputs are treated as untrusted strings and quarantined from execution control flows.

## 3. Multi-Tenant Isolation with PostgreSQL Row-Level Security (RLS)

### 3.1 Kernel-Level Policy Enforcement
To prevent cross-tenant data contamination, Row-Level Security is enabled across all tenant tables:
```sql
-- Enable RLS on core tables
ALTER TABLE leads ENABLE ROW LEVEL SECURITY;
ALTER TABLE deals ENABLE ROW LEVEL SECURITY;
ALTER TABLE documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE document_chunks ENABLE ROW LEVEL SECURITY;
ALTER TABLE voice_sessions ENABLE ROW LEVEL SECURITY;

-- Tenant Isolation Restrictive Policy
CREATE POLICY tenant_isolation_leads ON leads
  AS RESTRICTIVE
  USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);

CREATE POLICY tenant_isolation_documents ON documents
  AS RESTRICTIVE
  USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);

CREATE POLICY tenant_isolation_chunks ON document_chunks
  AS RESTRICTIVE
  USING (tenant_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid);
```

### 3.2 Session Variable Binding
Every database connection retrieved from the pool sets the tenant identifier within the active transaction:
```javascript
async function withTenantContext(tenantId, queryCallback) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    await client.query('SET LOCAL app.current_tenant_id = $1', [tenantId]);
    const result = await queryCallback(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}
```

## 4. Confirmation Gates for Destructive Actions

Tools are partitioned into deterministic risk tiers:

```
┌─────────────────────────────────┐
│     TIER 1: SAFE_READ TOOLS     │  ──► Auto-executed without user delay
│  • get_leads, get_deal_pipeline │
│  • search_knowledge_base        │
└─────────────────────────────────┘

┌─────────────────────────────────┐
│  TIER 2: DESTRUCTIVE_WRITE TOOLS│  ──► Requires User Confirmation Card:
│  • create_lead, update_deal     │      [Approve] ──► Tokenized Signed Execution
│  • send_outreach_email          │      [Reject]  ──► Abort & Retain State
│  • delete_record, enrich_lead   │
└─────────────────────────────────┘
```

When an agent suggests a Tier-2 tool:
1. The assistant emits a `tool_call_pending_approval` event containing the exact proposed arguments.
2. The UI renders an interactive Approval Card.
3. The user clicks **Approve** or **Reject**.
4. The client dispatches a cryptographically signed confirmation containing `tool_call_id`, `user_id`, and `timestamp`.
5. The backend validates the signature before executing the tool.

## 5. Audit Logging & Non-Repudiation

Every security-sensitive event produces an immutable audit record stored in `audit_events`:
- **Captured Metadata**: Event ID, Timestamp (UTC), Tenant ID, User ID, Client IP, User-Agent, Action Name, Target Resource ID, Outcome (`SUCCESS` / `FAILURE` / `BLOCKED`), and Request Hash.
- **Tamper Evidence**: Every audit entry includes an HMAC-SHA256 signature chained to the previous record hash (Merkle-tree log auditing).
